# 修复手机课表捏合缩放卡顿：预计算档位排布 + 平滑过渡动画

## 目标

消除手机课表**双指缩放过程中**每帧的整表强制重排，让捏合过程跟手顺滑，并让档位落定
（松手 / ± 按钮 / 双击）也从「实时重算文字排布」改为「套用预先算好的档位排布 + 一段动画」。

## 背景与证据

用户反馈原话：「现在缩放的时候会实时重新渲染文字排布，很卡，能不能提前批量计算好 1、1.5、2
这几个档位的排布，然后用一个比较流畅的动画进行缩放」。

本机生产构建 + CDP 真实触摸的基线读数（Chrome 155 / 412×731 / 18 格 / 未降速，见 `research/README.md`）：

- 双指 1x→2x 手势期间**最大帧间隔 200ms**、最重长任务 **202ms**、每轮 35–64 个 ≥50ms 长任务；
  松手后 800ms 窗口是 16.8ms 帧间隔 + 零长任务 ⇒ 卡顿全在**手势期间**。
- CPU profile 归因：`overflows()`（`content.scrollHeight > content.clientHeight + 1`）占**67.3%** 采样时间。
  `fitCourseCells()` 每个阶段「先写 DOM 再读 `scrollHeight`」，最多 **9N 次强制布局/帧**（18 格 → 162 次）。
- 控制组（离屏克隆网格，零 JS 测量）仍有 56ms 最重长任务、1400ms 只画 51 帧（~36fps）
  ⇒ 只「冻结 JS 测量」不足以顺滑，「真实改宽度 + 引擎重排」本身就撑不到 60fps。
- 预览路径（同一克隆改用 `transform: translateX + scaleX`，合成器属性）**84 帧 = 满帧、
  最大帧间隔 16.8ms、零长任务**；叠加 3px 模糊后读数完全一致 ⇒ **模糊不额外付费**。

同一类热点在 `10-11-schedule-week-swipe-jank` 修过（那次是松手切周时新课程格集中挂载）；
捏合路径没被覆盖，本次修的就是它。

## 需求

- **R1（手势期零重排）**：双指捏合期间不改变网格宽度、不跑任何课程格测量；预览走合成层
  变换（`scaleX` + 平移）并叠加模糊，跟手 1:1。判据是手势期间无 ≥50ms 主线程长任务、最大帧间隔 ≤50ms。
- **R2（批量预计算档位排布）**：1x / 1.5x / 2x 三档的每格适配结果（丢弃了哪几行、兜底系数、
  文字块宽度）在用户操作之前批量算好并缓存；档位落定时按缓存**纯写套用**（零测量读取）。
- **R3（平滑过渡动画）**：档位落定不是硬跳变 —— 预览比例用一段合成器动画过渡到目标档位比例，
  动画结束后一次性把真实宽度与预计算排布落定，并清除变换与模糊。
- **R4（三条入口一致）**：双指捏合、`−`/`+` 按钮、双击切换都走同一套「预览 → 过渡 → 落定」路径。
- **R5（保留既有语义与契约）**：1x 恰好铺满不产生横向滚动；档位仍只有 1 / 1.5 / 2；字号仍在 8–15px；
  丢弃优先级、教室恒显、单双周标签、非本周淡化、缺勤痕迹、空间自适应判据全部不变；
  缩放值仍不持久化（进页面 1x）。
- **R6（不与既有手势互相破坏）**：边缘阻尼切周的手势互斥规则、单指纵向滚动、课程格点按、
  双击去抖、`setPointerCapture` 的 try/catch 全部保持；预览期的变换不得污染
  `[data-schedule-scroll]` 的 `scrollWidth` / 边缘判定。
- **R7（无障碍与降级）**：`prefers-reduced-motion: reduce` 时不播放过渡动画，直接落定；
  预计算尚未就绪或任何一步失败时，必须回退到「实测适配」这条既有正确路径，不得显示错误排布。

## 验收标准

- **AC1（R1）**：同夹具、同视口、同引擎、未降速 CPU 下，双指 1x→2x 与 2x→1x 各 2 轮，
  手势期间（`touchStart` → `touchEnd` 窗口）**无 ≥50ms 长任务、最大帧间隔 ≤50ms**；
  保留修复前后读数。基线是 200ms / 202ms。
- **AC2（R2）**：单测钉死「缓存命中时零测量读取」：对带快照的课程格调用套用路径，
  任何 `overflows()` / `readUsedWidth()` 读取被调用即测试失败。
- **AC3（R2/R3）**：档位落定后的静止态：`transform` / `filter` 内联值清空
  （computed 为 `none`）、网格 `min-width` 等于该档位对应值、`data-zoom-level` 等于该档位、
  `data-zoom-preview` 属性不存在。
- **AC4（R3/R4）**：三条入口都到达同一终态；`±` 与双击的过渡动画时长与缓动由常量单一真源给出，
  且被单测钉住；`prefers-reduced-motion: reduce` 下过渡时长为 0 且终态一致。
- **AC5（R5）**：三视口（360×794 / 412×731 / 1440×900）× 1x/1.5x/2x 逐格断言
  教室恒显、可丢行顺序不倒挂、字号在 8–15px、文字块不宽于容器且不水平溢出、
  内容溢出必须已走兜底（`scrollHeight ≤ clientHeight + 1`）；历史基线 violations = 0。
- **AC6（R6）**：切周手势回归通过（一次手势只切一周、结束态 `idle`、无残留 transform/opacity）；
  预览期与结束后 `[data-schedule-scroll]` 的 `scrollWidth` 不带入缩放预览造成的污染。
- **AC7（R7 + 门禁）**：`pnpm test`、`typecheck`、`lint`、`format:check`、`build`、
  `webview:check-css`、`test:android-assets` 全绿；相关源码守卫（`scheduleSourceGuard.test.ts`）更新后通过。

## 范围外

- 不改课程数据、配色分配、周次边界、持久化格式与手势动画方向。
- 不新增缩放档位（仍是 1 / 1.5 / 2），不改信息分级阈值。
- 不重设计课表布局、不引入相邻周预渲染、不做虚拟滚动。
- 不处理桌面端的缩放（桌面本就不启用缩放）。
- 不发布版本、不自动提交。
- 真机（Android WebView）与用户设备复核不在本轮范围内；本轮验收环境是本机桌面 Chrome（软件栅格化），
  结论写成同环境内的相对比较。

## 风险与待确认

- **与既有规范的冲突（已由用户拍板）**：`mobile-schedule-layout.md` 明写「缩放只改列宽，
  不引入任何等比缩放（不用 CSS `zoom`、不用 `transform: scale`）」。本任务引入的
  transform 预览是**仅存在于手势/过渡期间**的受控例外，静止态必须清零，并由源码守卫 + AC3 钉住；
  规范需在同一任务内更新（Phase 3.3），否则下一轮会被当成回归修掉。
- **预览与真实排布的差异**：`scaleX(k)` 会把文字横向拉伸，且预览期显示的档位排布来自**原档位**
  （例如 1x 的排布被拉伸到 2x），落定时文字会从「拉伸态」纠正为「2x 真实态」。这是「相机式变焦
  后落定」的固有意象，由过渡动画与模糊掩盖；若真机观感不佳，退路是缩短过渡时长或减小预览幅度。
- **预计算预热的一次性成本**：离屏克隆整张网格并跑一次适配，代价与今天的一帧适配同量级
  （~50–180ms）。它必须在**空闲窗口**执行、且任何手势/滚动立刻取消；否则会自己制造卡顿。
- **首访档位的回退**：预计算未就绪时按 R7 回退到实测适配，那一档的落定会有一次卡顿（与今天相同）。
- 未闭环项：本机软件栅格化读数不等于真机 GPU 读数；具体改善幅度需在具备真机环境时补测。
